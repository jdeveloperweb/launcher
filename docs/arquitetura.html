1 Visão geral e a fronteira

O SCCI roda um launcher (daemon Pascal) que faz a ponte entre o front web e os programas “w” (wtela, wmenu, wdoc…). O launcher não é a regra de negócio — ele transporta: recebe o HTTP, decifra, valida a sessão, monta o ambiente, executa o programa real e fala o protocolo de blocos do oserver com ele.

O reator Java reproduz exatamente esse papel, do jeito hexagonal, e não reimplementa a lógica dos programas. A fronteira é o oserver: abaixo dela, os programas continuam donos da regra; o reator só monta o ambiente e conversa o protocolo.

Por quê assim: zero reimplementação de regra de programa mantém o risco baixo e o contrato byte-a-byte com o front. Só o transporte virou Java.

2 Camadas hexagonais (Ports & Adapters)

A dependência aponta sempre para dentro. O núcleo não conhece framework.

A regra da dependência

  • domain não conhece ninguém (nem Spring). Modelos, ports e regra técnica pura (WcopCrypto, PasswordPolicy).
  • application depende só de domain. POJOs puros, sem anotação.
  • adapters (in/out) dependem de application+domain, nunca o contrário.
  • bootstrap é o único que conhece todos (wiring + component-scan).

5 Fluxos ponta a ponta

Login  POST /w/login

AutenticacaoController decifra o blob AES (WcopCrypto) → LoginService → SccCredenciaisRepository lê a base do ambiente → VerificadorSenhaBcryptMd5 compara md5crypt → em sucesso, SessaoService.registrar grava na SCCI_SESSION + cache Redis → resposta {success, sessionKey, contexto} cifrada em XOR.

Despacho POST /w  (executar um programa)

DespachoController decifra → VALIDA a sessão → DespachoService → ProgramExecutor: monta env (com USER=<usuário>), resolve o binário, converte params JSON→<PMEMORY>, monta os blocos e executa via NativeOserverBridge (socketpair) → lê o 1º bloco → resposta cifrada. A autorização por operação acontece dentro do programa (UsuarioTemPerm(getenv('USER'))).

Documentos /sccidoc

  • Ler/baixar (POST body): DocumentoService → params size-prefixed [LE32] → resposta [len][XML metadados][binário] → arquivo (mime por extensão) ou JSON.
  • Ver no navegador (AbrirUrl, GET): /sccidoc/{programa}/{metodo}?query → programa/método do path, params da query, auth por cookie → arquivo inline.
  • Enviar (Importar, multipart): EnvioDocumentoService → 1 chamada/arquivo, [LE32][XML+FileName]+bytes → PostX → respostas JSON juntadas (com o prefixo [LE32] removido, como o ReadAnsiString faz).

Multi-banco — pronto (drivers + queries portáveis)

Cada cliente aponta para o seu banco no launcherenv.ini ([USERS]); o JdbcConnectionFactory monta a URL pelo DRIVERNAME. Portar um cliente novo do mesmo tipo de banco = configuração.

Queries portáveis entre bancos: tudo ANSI-padrão e parametrizado (?), sem funções específicas de banco (NOW()/SYSDATE/GETDATE()), sem LIMIT/TOP/::cast/ILIKE. Datas via setTimestamp (Java); tabela e colunas vêm do launcherenv.ini por cliente. Só o SELECT 1/COUNT(*)/UPDATE/DELETE e atribuição coluna-a-coluna (NO_SENHA1=NO_SENHA2) — roda igual nos 4.

Build: mvn -q clean package → launcher/bootstrap/target/launcher.jar.  Deploy: deploy/ (envia jar + kong.yml, sobe via run.sh 8083, JDK 21 embutido, sem cron).
