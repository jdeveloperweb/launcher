01 — O que temos hoje

Uma borda fina na frente, dois backends atrás.

O front fala só com o launcher. Ele não contém regra de negócio: transporta o protocolo W_COP, decide por feature-flag quem atende cada chamada e delega — para o scci-core (domínios já em Java) ou para o pascal-executor (o que ainda é Pascal).

02 — As quatro peças

O que é cada coisa — e o que tem dentro.

O repositório (launcher/) é o guarda-chuva. Dentro, quatro grupos com papéis distintos. Regra DDD: um contexto só referencia a porta do outro, nunca a entidade.

app · edge

launcher/ — a borda

O gateway fino. Traduz o mundo do front (W_COP, sessão, /w e /sccidoc) e orquestra: decide e chama. Não tem lógica de negócio nem código nativo.
  • adapters-in — controllers /w/*, /sccidoc
  • application — SessaoService (gate) + roteadores Strangler
  • adapters-out — clientes REST (scci-core, pascal-executor), Redis, SCCI_SESSION
  • domain — modelos + portas (ResultadoLogin, Sessao, ...)
porta 8083estado Java puro (sem JNA)escala horizontal
app · domínios

scci-core/ — o monólito modular

Onde a regra migrada vive, em Java. DDD: um módulo por bounded context, cada um com sua hexagonal interna. Um deployable, N réplicas.
  • acesso — login (BANCO + família B), senha, recuperação, valida
  • sessao — ciclo de vida (Redis + SCCI_SESSION)
  • documentos — ver / baixar / enviar (FileSystem + BLOB)
  • notificacao — e-mail/SMTP, reaproveitável
  • kernel · bootstrap — infra JDBC multi-banco + main
porta 8090estilo DDD + hexagonalescala horizontal
app · legado

pascal-executor/ — a âncora legada

O único módulo com nativo. Isola a ponte oserver (JNA: socketpair + posix_spawn no fd 6) que spawna os programas Pascal. Co-localizado com os binários; encolhe até o decommission.
  • NativeOserverBridge — a ponte JNA/libc
  • ProgramExecutor — protocolo de blocos do oserver
  • ExecutarController — REST /interno/executar (binário base64)
porta 8091preso à caixa do Pascalfuturo desligar
libs · in-process

common/ — o compartilhado

Módulos técnicos usados in-process pelos apps — sem regra de domínio. Único ponto onde a estrutura é inglês; o negócio segue em PT.
  • crypto — W_COP (AES no request, XOR na resposta)
  • environment — leitor do launcherenv.ini + JDBC multi-banco
  • contract — contratos compartilhados

04 — Como tudo se conecta

Os fios entre as peças.

Comunicação interna é REST HTTP local (sub-milissegundo, mesmo host). O estado de sessão é um contrato de Redis compartilhado; o banco de cada cliente é resolvido por request.

Contrato de wire. launcher e scci-core são processos separados que compartilham o Redis; o formato da chave é idêntico nos dois (provado por teste cruzado). O W_COP fica só na borda — o interno trafega texto na rede confiável.
05 — Feature flags (Strangler)

Como o roteador foi desenhado — e como pode evoluir.

Cada canal do launcher é um decorator (roteador) que, por flag, escolhe o caminho JAVA (scci-core) ou o legado (Pascal). Sem entrada = comportamento antigo. Com o scci-core fora, o cliente cai no fallback — resiliência embutida.

06 — Como escala

O que escala livre, e o que fica preso.

launcher e scci-core são stateless — o estado vive no Redis compartilhado e nos bancos. Logo, escalam em N réplicas atrás de um balanceador. O pascal-executor é pinado à caixa legada (precisa dos binários + oserver + ambiente em disco).

Por que funciona. Tirar o JNA do launcher foi o que o tornou portável: edge 100% Java roda em container e escala sem arrastar a caixa legada junto.
07 — Onde a migração está

Strangler em progresso: o Java cresce, o Pascal encolhe.

Java já no scci-core — validado ao vivo

  • documentos — download (FileSystem + BLOB) e upload, byte-idêntico ao legado
  • acesso — login BANCO + família B (7 clientes), troca de senha, valida
  • sessao — Redis + SCCI_SESSION, contrato de Redis provado entre processos
  • notificacao — e-mail extraído para contexto próprio
  • execução — externalizada no pascal-executor; launcher virou Java puro

Pascal ainda via pascal-executor

  • demais métodos do wdoc/wtela/... não migrados
  • relatórios e fluxos que ainda batem no oserver
  • cada um migra atrás de flag, um de cada vez, com fallback
  • ao fim: desligar o pascal-executor — sem cirurgia no launcher
invariantes de segurança
Login = somente leitura — sem rehash md5crypt→bcrypt
W_COP fica na borda — o interno trafega texto na rede confiável
Produção /aejs intocada — tudo no trilho paralelo /aejs-l
Redis: contrato idêntico — mesmo formato de chave nos dois processos
Ir ao ar por cliente — exige endpoint/credenciais daquele cliente
Escrita só com OK — provisão/senha em ambiente nomeado
